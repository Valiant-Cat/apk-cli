# APK/AAB 包信息修改 CLI 设计说明

## 1. 背景与目标

本项目目标是实现一个基于 Node.js 的命令行工具，用于直接处理现成的 `apk` / `aab` 文件，在不污染原始输入文件的前提下，完成以下修改并重新生成可交付产物：

- 应用名称
- 应用图标
- 版本号信息
- 包名 / applicationId
- 重新签名

首版工具面向“常见 Android 包修改”场景，优先追求高成功率、可诊断性和可维护性，不追求覆盖所有加固、重混淆或强定制包。

## 2. 范围

### 2.1 首版支持

- 实现语言：`Node.js`
- 输入：现成的 `apk` / `aab` 文件路径
- 输出：修改后的新 `apk` / `aab` 文件
- 签名：必须使用用户提供的 `keystore` 重新签名
- 图标修改范围：
  - 主应用图标
  - `roundIcon`
  - 自适应图标前景 / 背景
- 名称修改范围：
  - 默认 `label`
  - 命中的字符串资源
  - 多语言字符串资源
- 版本信息修改范围：
  - `versionName`
  - `versionCode`
  - `packageName` / `applicationId`
- 依赖策略：
  - 优先使用本机已有工具
  - 缺失时允许自动下载并缓存
- CLI 结构：
  - `apk-cli edit <input>`
  - `apk-cli inspect <input>`
  - `apk-cli doctor`

### 2.2 首版不支持

- 直接处理反编译目录
- GUI 界面
- 批量并发处理多个包
- 交互式签名向导
- 保证修复所有业务代码 / smali 中的硬编码包名
- 保证覆盖所有极端加固、混淆、定制 ROM 图标方案
- 上架合规审查能力

## 3. 设计原则

### 3.1 高成功率优先

打包、对齐、签名等环节优先复用成熟 Android 工具链；项目自研部分聚焦在资源解析、引用追踪、修改器编排和错误输出。

### 3.2 输入零污染

工具不直接修改输入文件。无论成功或失败，原始 `apk` / `aab` 保持不变。所有操作在独立工作目录内完成。

### 3.3 失败可诊断

每个阶段必须产生结构化结果，至少说明：

- 当前阶段名称
- 执行的工具 / 命令
- 成功或失败
- 修改了什么
- 没修改什么
- 失败原因
- 中间产物路径

### 3.4 功能边界清晰

包名修改是高风险项，首版采用“核心元数据必改、常见引用尽量改、不可确认项明确报告”的策略，而不是承诺无条件全量修复。

## 4. 总体方案对比

### 4.1 方案 A：纯编排外部工具

优点：实现快。

缺点：内部能力薄弱，资源修改逻辑分散，后续维护成本高。

### 4.2 方案 B：外部工具链 + Node 原生资源编辑层

优点：

- 解包、重打包、签名复用成熟工具
- 名称 / 图标 / 版本 / 包名修改统一收敛到内部模型
- 易扩展 `inspect` / `doctor` / 规则校验

缺点：

- 首版实现复杂度中等

### 4.3 方案 C：尽量自实现打包链路

优点：理论控制力高。

缺点：Android 打包链路复杂，不适合首版。

### 4.4 结论

采用方案 B：外部工具链 + Node 原生资源编辑层。

## 5. 系统架构

整体划分为三层。

### 5.1 toolchain

职责：

- 探测本机工具
- 下载缺失工具
- 缓存工具
- 封装命令调用
- 归一化工具报错

涉及工具包括：

- `java`
- `apktool`
- `bundletool`
- `jarsigner`
- `zipalign`
- `aapt2`

### 5.2 package-editor

职责：

- 根据输入类型选择 APK 或 AAB 处理链路
- 建立工作目录
- 解包
- 构建内部资源索引
- 调用修改器
- 重新打包
- 重新签名
- 结果校验

### 5.3 mutations

职责：

- 名称修改器
- 图标修改器
- 版本修改器
- 包名修改器

每个修改器必须返回结构化修改报告：

- 目标值
- 实际命中的文件 / 资源
- 修改成功项
- 未覆盖项
- 风险提示

## 6. 命令设计

### 6.1 `apk-cli edit <input>`

主命令，负责解包、修改、重打包、签名与产物输出。

建议参数：

```bash
apk-cli edit app.apk \
  --output dist/app-modified.apk \
  --app-name "新名称" \
  --icon /path/icon.png \
  --version-name 2.3.4 \
  --version-code 20304 \
  --package-name com.example.newapp \
  --keystore /path/release.jks \
  --store-pass xxx \
  --key-alias release \
  --key-pass xxx
```

辅助参数：

- `--work-dir`
- `--keep-work-dir`
- `--tool-cache-dir`
- `--download-missing-tools`
- `--verbose`
- `--json`

### 6.2 `apk-cli inspect <input>`

只读分析命令，用于输出：

- 包类型
- 当前包名
- 当前版本信息
- app name 解析结果
- launcher 入口信息
- 图标引用链
- 常见风险提示

### 6.3 `apk-cli doctor`

环境诊断命令，用于检测：

- Java 运行环境
- Android 工具链可用性
- 工具版本
- 自动下载能力
- 缓存目录权限

## 7. 标准处理流程

`edit` 命令按以下 9 个阶段执行。

### 7.1 输入校验

检查：

- 输入文件存在
- 扩展名合法
- 签名参数完整
- 输出路径不覆盖输入文件

### 7.2 工具链探测

- 优先使用本机工具
- 缺失时按需下载到缓存目录
- 仍缺失则直接失败

### 7.3 建立工作目录

- 创建独立临时目录
- 拷贝输入文件
- 建立日志目录和中间产物目录

### 7.4 解包

- APK：通过 `apktool` 解包
- AAB：通过 bundle 解包链路处理

### 7.5 构建资源索引

解析并建立统一索引：

- Manifest
- app label
- launcher activities / aliases
- `icon` / `roundIcon`
- adaptive icon XML
- 版本信息
- 包名 / applicationId
- 常见字符串与资源引用图

### 7.6 执行修改器

#### 名称修改器

- 修改 manifest 直接文本或资源引用
- 修改 `strings.xml` 及命中的多语言字符串资源
- 生成未命中报告

#### 图标修改器

覆盖范围为“2.5”策略：

- 主应用图标
- `roundIcon`
- adaptive icon 前景 / 背景

不做全包所有疑似图标资源穷举替换。

#### 版本修改器

- 修改 `versionName`
- 修改 `versionCode`

#### 包名修改器

必改：

- Manifest 包名 / applicationId

尽量修改：

- 常见资源与明文引用
- 常见 authority / provider / provider-like 引用

不承诺：

- 业务逻辑中的所有硬编码字符串或 smali 常量全部修复

### 7.7 重新打包

- 生成新的中间包
- 保留打包日志
- 打包失败则停止流程

### 7.8 重新签名

- 使用用户提供的 `keystore`
- APK 再执行 `zipalign`
- 签名失败不得输出成功结论

### 7.9 结果校验

对最终产物重新执行一次 `inspect`，核对：

- 名称是否生效
- 图标引用是否生效
- 版本信息是否生效
- 包名是否达到预期

校验通过后才视为成功。

## 8. 回滚与失败策略

本项目的回滚策略是“输入零污染”，而不是“就地恢复”。

### 8.1 失败规则

- 任一步失败都不得覆盖原始输入文件
- 默认失败时保留工作目录便于排查
- 用户指定 `--keep-work-dir` 时，无论成功失败都保留工作目录

### 8.2 阶段报告

每个阶段必须输出：

- 阶段名
- 是否成功
- 关键日志
- 产物路径
- 错误摘要
- 下一步建议

### 8.3 包名修改风险提示

若包名修改存在未覆盖项，工具必须明确提示：

- 已修改项
- 未修改项
- 可能的运行风险
- 建议人工复核范围

## 9. 测试策略

### 9.1 单元测试

覆盖：

- 参数解析
- 工具探测逻辑
- Manifest 解析
- 资源索引构建
- 名称 / 图标 / 版本 / 包名修改器

### 9.2 集成测试

使用最小示例 `apk/aab`：

- `inspect` 输出正确
- `edit` 可成功生成新产物
- 产物签名成功
- 关键字段发生预期变化

### 9.3 回归夹具

样本至少包括：

- 普通 PNG 图标包
- round icon 包
- adaptive icon 包
- 多语言 app name 包
- 带常见包名引用的样本包

### 9.4 命令级 smoke test

覆盖：

- `doctor`
- `inspect`
- `edit --help`
- 最小参数的 `edit`

## 10. 交付物清单

实现阶段预期产物：

- CLI 源码
- 可执行入口
- `doctor` / `inspect` / `edit` 三个命令
- 工具下载与缓存模块
- 资源解析与修改器模块
- 自动化测试
- 示例夹具
- README 使用文档
- 设计文档
- 实施计划文档

## 11. 验收标准

首版视为完成，需要满足：

- 常见 APK 可稳定修改名称、图标、版本、包名并重新签名
- 常见 AAB 可完成 inspect、修改、重新产物化
- 缺失依赖时能明确提示或自动下载
- 任一步失败都能定位到具体阶段
- 输入原文件始终不被污染

## 12. 风险与后续演进

### 12.1 当前风险

- 包名修改天然存在未完全覆盖风险
- AAB 处理链路较 APK 更复杂
- 三方工具版本差异可能影响稳定性

### 12.2 后续可扩展方向

- 增加环境变量或交互式密码输入
- 增加批量模式
- 增加更细粒度包名引用修复器
- 增加产物差异报告
- 增加更强的规则诊断和合规提示
